# 2026-04-21 Mini-SGLang c10d Synthetic Results

## Scope

Answer the higher-confidence question that the earlier external Gloo proxy could not:

- if Mini-SGLang used a custom CPU process group backend in PyTorch c10d, what is the
  retained delta between `uv` and Myelon on the exact CPU control-plane operations that
  Mini-SGLang actually issues?

This uses a real out-of-tree c10d backend implemented in:

- `benchmark/synthetic/c10d_glooext/setup.py`
- `benchmark/synthetic/c10d_glooext/src/backend.cpp`

The backend links against the external `gloo/build-mpi-uv/gloo/libgloo.a` and selects
`uv` or `myelon` via `MINISGL_C10D_GLOOEXT_TRANSPORT`.

## Environment

- `uv 0.9.26`
- Python `3.12.10`
- `torch 2.9.1`
- `numpy 2.4.4`
- `ninja 1.13.0`

## Command

```bash
python benchmark/synthetic/bench_c10d_control_plane.py \
  --world-size=4 \
  --warmup=20 \
  --iterations=100
```

## Benchmarked call shapes

- `barrier`
  exact proxy for `SchedulerIOMixin.sync_all_ranks()`
- `scheduler_count_broadcast`
  exact proxy for scheduler rank0 broadcasting the pending raw-message count as an `int64`
  CPU tensor
- `pynccl_uid_broadcast_object`
  PyTorch-level proxy for `init_pynccl(... broadcast_object_list ...)` with a NCCL-like
  unique-ID payload
- `free_mem_min_allreduce`
  exact proxy for `Engine._sync_get_memory()` reducing `[free, -free]` as two `int64`
  CPU values with `ReduceOp.MIN`

## Important implementation note

The first c10d backend draft assigned a fresh Gloo tag to every operation. That badly
distorted the Myelon numbers because the current transport partitions same-node SHM
channels by tag. Sequential c10d traffic should not pay that setup cost on every
iteration, so the retained numbers below use stable per-op tags instead.

This matters because after fixing the tag behavior, the c10d results aligned with the
earlier external Gloo benchmark direction instead of contradicting it.

## Retained takeaways

- The c10d route is viable on this host.
- The custom backend is not just a transport-only proxy anymore; it is exercising the
  real `torch.distributed` API layer.
- For the exact Mini-SGLang CPU control-plane operations we care about, Myelon is
  consistently faster than both:
  - the same c10d backend running on `uv`
  - the builtin wheel-backed `gloo`
- The strongest retained win in this probe is the object fanout path:
  `broadcast_object_list` dropped from roughly `265-266 us` on builtin `gloo` to
  `114-119 us` on Myelon.
- The tiny `ReduceOp.MIN` allreduce used by `_sync_get_memory()` also improved
  materially, from roughly `288-292 us` on builtin `gloo` to `154 us` on Myelon.

## Caveats

- `init_process_group` was materially noisier than the steady-state collectives, so the
  collective numbers are the more trustworthy retained signal.
- This is still synthetic. It is accurate for Mini-SGLang's CPU control-plane API
  shapes, but it is not a claim about full end-to-end serving throughput on Linux + CUDA.
